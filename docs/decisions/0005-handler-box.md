# ADR 0005. 핸들러 상자 (v3)

상태: 채택 (엔진 v3, v4가 포함) · 2026-11-12

## 배경

- 렌더마다 클릭 핸들러가 새 함수로 만들어집니다. 함수는 `===` 비교가 달라서, 핸들러만 바뀐 요소도 `PROPS` 명령이 됩니다.
- v2에서 오목 첫 착수 직후 타이머 1회 커밋은 `PROPS` 231건이었고, 그 DOM 반영에서 리스너 API(`addEventListener`, `removeEventListener`)가 462번 호출되었습니다. 요소마다 옛 리스너를 떼고 새 리스너를 붙이기 때문입니다.
- 핸들러만 바뀐 경우는 화면이 달라지지 않습니다. 이 호출은 낭비입니다.
- 자식 컴포넌트는 Hook을 쓸 수 없습니다(과제 조건). 그래서 핸들러를 안정적으로 유지하는 일반적인 방법(`useCallback`)을 쓸 수 없습니다. 엔진이 해결해야 했습니다.

## 결정

요소마다 리스너는 이벤트당 하나만 붙이고, 최신 핸들러는 요소별 표(핸들러 상자)에서 찾아 부릅니다. 핸들러 교체는 이 표의 값만 바꿉니다.

| 요소 | 동작 | 구현 위치 |
| --- | --- | --- |
| 공용 리스너 | 요소의 이벤트마다 `sharedListener` 하나를 한 번만 붙입니다. 이벤트가 오면 표에서 그 이벤트의 최신 핸들러를 찾아 호출합니다. | `engines/v3-handlers/vdom.js` `sharedListener`, `setProp` |
| 핸들러 교체 | `setHandler` 가 표의 값만 바꿉니다. DOM API를 부르지 않습니다. | `vdom.js` `setHandler` |
| 새 명령 `HANDLERS` | 같은 이벤트 속성이 함수에서 다른 함수로 바뀌면 `PROPS` 대신 `HANDLERS` 명령을 만듭니다. 같은 요소의 `PROPS` 앞에 둡니다. | `diff.js` (`HANDLERS` 명령 생성), `patch.js` (`HANDLERS` 분기) |
| 생기거나 사라지는 핸들러 | 이전에 함수가 없던 곳이나 함수가 없어지는 곳은 그대로 `PROPS` 입니다. 이때만 리스너를 붙이거나 뗍니다. | `vdom.js` `setProp` |
| 보고 | `countPatches` 에 `HANDLERS` 칸이 있어 `PROPS` 와 따로 셉니다. | `component.js` `countPatches` |

- `engines/v3-handlers/` 는 v2를 바탕으로 `vdom.js`, `diff.js`, `patch.js`, `component.js` 일부를 고친 것입니다. 배칭은 v2와 같습니다.

## 고려한 대안

| 대안 | 얻는 것 | 내주는 것 | 판단 |
| --- | --- | --- | --- |
| 가. 핸들러 상자 + `HANDLERS` 명령 | 리스너 API 호출이 사라집니다. 변경 명령이 두 모듈 사이의 계약이라는 구조를 그대로 씁니다. 요소별 리스너 방식과 DOM 이벤트 동작이 같습니다. | 명령이 5종에서 6종이 됩니다. `diff` 와 `patch` 가 모두 새 명령을 알아야 합니다. | 채택 |
| 나. 루트 컨테이너 이벤트 위임 | 리스너가 루트에 이벤트당 하나뿐입니다. 실제 React와 같은 방향입니다. | 버블링하지 않는 이벤트를 따로 다뤄야 하고, 어느 요소의 핸들러인지 찾는 경로 계산이 필요합니다. 전파를 멈추는 동작의 의미도 달라집니다. | 기각 |
| 다. 자식에서 `useCallback` 으로 핸들러 고정 | 앱 코드만으로 해결됩니다. | 자식 컴포넌트의 Hook은 과제 조건상 예외입니다. 루트에서 만든 함수를 자식에 모두 전달해야 합니다. | 기각 (사용 불가) |

## 결과와 비용

같은 시나리오(오목 첫 착수 직후 타이머 1회, 실제 브라우저 헤드리스 Edge, 마지막 커밋)에서 엔진만 바꿔 측정했습니다.

| 엔진 | `PROPS` | `HANDLERS` | 리스너 API 호출 |
| --- | :---: | :---: | :---: |
| v2 | 231 | 0 | 462 |
| v3 | 0 | 231 | 0 |

- 줄어든 것은 리스너 API 호출입니다. DOM 변경 수(MutationObserver로 센 값)는 v2와 v3이 같습니다. 핸들러 교체는 원래 DOM에 보이는 변화가 아니기 때문입니다.
- 명령 수 자체는 줄지 않고 `PROPS` 에서 `HANDLERS` 로 옮겨 갑니다. 줄어드는 것은 명령 한 건을 처리하는 비용입니다.

| 얻은 것 | 낸 비용 |
| --- | --- |
| 핸들러만 바뀌는 렌더에서 리스너 API 호출이 0입니다. | 변경 명령이 6종이 되어 `diff` 와 `patch` 가 모두 `HANDLERS` 를 알아야 합니다. |
| 앱 코드를 바꾸지 않아도 됩니다. | 요소마다 핸들러 표가 하나씩 더 생깁니다. |
| 클릭 시점에는 항상 최신 핸들러가 불립니다. | 핸들러 호출이 공용 리스너를 한 번 거칩니다. |

## 검증

`npm test` 를 2026-11-12 에 실행했을 때 643개 테스트가 통과했습니다(러너 집계 644는 test/helpers.js 포함, 실패 0). v3 전용 테스트는 `test/v3-handlers.test.js` 이고 v3, v4 두 엔진에서 같이 돌립니다. 공통 테스트는 v2, v3, v4 세 엔진에서 같이 돌립니다.

| 확인하는 것 | 테스트 이름 |
| --- | --- |
| 명령 생성 | "핸들러만 바뀌면 PROPS 대신 HANDLERS 하나", "핸들러가 생기거나 사라지면 PROPS", "핸들러와 속성이 같이 바뀌면 HANDLERS 가 PROPS 앞" |
| 최신 핸들러 호출 | "HANDLERS 뒤 클릭은 최신 핸들러를 부른다" |
| 리스너 정리 | "핸들러가 사라지면 리스너도 떼어진다" |
| DOM API 호출 없음 | "HANDLERS 적용은 addEventListener · removeEventListener 를 부르지 않는다" |
| 보고 | "countPatches 에 HANDLERS 키가 있다" |

- 오목 페이지 수준에서는 `test/omok-page.test.js` 의 "[v3-handlers] 타이머 1회 커밋은 PROPS 0, HANDLERS > 0, 리스너 API 0" 이 확인하고, "[v2-microtask] 착수 뒤 타이머 커밋은 리스너 API 호출이 0 보다 크다" 가 세기 장치가 동작하는지 대조합니다.
- 위 결과 표의 수치(231, 462)는 브라우저 측정값이며 자동 테스트가 고정한 값이 아닙니다.

## 하지 않은 것

| 항목 | 이유 |
| --- | --- |
| 이벤트 위임 | 위 대안 나. 비용이 큽니다. |
| 핸들러가 생기거나 사라지는 경우를 `HANDLERS` 로 처리 | 리스너를 붙이거나 떼야 하므로 `PROPS` 의 일입니다. |
| 렌더 횟수 자체를 줄이는 구조 | 루트부터 전체를 다시 만드는 구조는 그대로입니다. |
